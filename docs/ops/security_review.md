## Находки

### 1. ВЫСОКАЯ. У API нет аутентификации, а дашборд проксирует его целиком наружу

**Где.** `web/next.config.mjs:15` — `{ source: "/api/backend/:path*", destination: "${target}/:path*" }`.
`leadcentre/api.py` — ни одной зависимости авторизации: `grep -niE 'auth|Depends|middleware|rate'`
по файлу даёт только `author`, `input_tokens`, `output_tokens` (ИЗМЕРЕНО).

**Почему это проблема.** Правило переписывает **любой** путь, поэтому посетитель публичной
страницы получает весь бэкенд на своём же origin — без CORS, без ключа, без ограничения частоты:

- `POST /api/backend/leads` → `POST /leads` (`api.py:482`) — каждый вызов идёт в платную
  модель: открытый кран по деньгам на аккаунте провайдера и по лимитам;
- `POST /api/backend/leads/{id}/approve` (`api.py:511`) — одобрение и отправка в CRM;
- `POST /api/backend/discover/run` (`api.py:584`) — обход внешнего реестра от нашего имени;
- `GET /api/backend/leads` (`api.py:487`) — весь корпус обращений с текстами;
- `POST /api/backend/leads/{id}/disagree` (`api.py:554`) — запись в базу.

Обещание в интерфейсе «Nothing is sent to the customer — a human presses the button»
(видно на скриншотах `01`, `02`, `02b`, `02c`, `02d`, `08`) по устройству кода верно: CRM
дёргается только из `approve` (`api.py:527`) и больше ниоткуда. Но «человек» здесь — кто
угодно, у кого есть ссылка. Ключи при этом не утекают, они остаются на сервере; утекает
право совершать действия, которые стоят денег и пишут в чужие системы.

**Что делать.** Публиковать дашборд в mock-режиме (`NEXT_PUBLIC_API_URL` пуст) — тогда
`rewrites()` возвращает `[]` и прокси не существует вовсе; это уже реализовано и для показа
нанимателю достаточно. Если нужен live — закрыть прокси токеном или basic-auth на стороне
Next и ограничить частоту `POST /leads` и `/discover/run`.

### 2. ВЫСОКАЯ. Вырезание персональных данных не сторожится ни одним тестом

**Где.** `leadcentre/engine/extract.py:188` — `scrub_pii`; вызовы `:541` (путь к модели) и
`:662` (offline-заглушка). Тесты: `grep -rn 'scrub_pii' tests/` — **0 совпадений**
(ИЗМЕРЕНО); ни одного теста на маску телефона, маску почты или на `has_contact`,
выведенный из вырезанного.

**Почему это проблема.** Это единственный механизм минимизации ПД во всём конвейере, и на
него ссылаются сразу три места как на гарантию: интерфейс («Mask contacts. Phone numbers and
e-mail addresses are cut out of the text before anything is sent to the model» —
`web/screenshots/03-new-request-form.png`), контракт CRM (`leadcentre/crm/base.py:27`:
«в `raw_text` кладётся уже вычищенный `scrub_pii` текст») и запись в базу
(`leadcentre/api.py:300`). Гарантия держится на строке кода, а не на гейте (Ц7).

**Сегодня механизм работает** — ИЗМЕРЕНО:

```
scrub_pii('пиши на a@b.com или +971 50 123 4567').text
  -> 'пиши на [email] или [phone]'
```

**Мутация (Т1), ИЗМЕРЕНО.** `scrub_pii` подменён на no-op (текст возвращается как есть) —
без правки репозитория, подменой из `sitecustomize` во временном каталоге на время прогона.
Подмена применилась:

```
с мутацией:  'пиши на a@b.com или +971 50 123 4567'
без мутации: 'пиши на [email] или [phone]'
```

Сюита при этом:

```
БЕЗ МУТАЦИИ: 576 passed
С МУТАЦИЕЙ:  576 passed        <- ни один тест не покраснел
```

То есть полное отключение вырезания ПД — ноль красных тестов. Обратная сторона: сегодняшнее
поведение верно, но следующая правка регулярки или порядка вызовов сломает его молча,
и телефон клиента уедет и в модель, и в базу, и в описание компании в HubSpot
(`leadcentre/crm/hubspot.py:122`: `"description": lead.raw_text[:1000]`).

**Что делать.** Тест с фикстурами с обоих краёв и из середины (Т3): текст с почтой, текст с
телефоном в трёх форматах, текст с «8 человек» и датой `2026-09` (не телефон, маскироваться
не должно — негативный контроль, И5), плюс проверка `has_contact` и счётчиков
`phones`/`emails`. Ожидаемые значения — литералами (Т2).

### 3. СРЕДНЯЯ. RLS включён, но политика отдаёт анониму на чтение все таблицы, включая тексты обращений

**Где.** `leadcentre/store/schema.sql:139-143` — включение RLS на пяти таблицах;
`:145-154` — цикл, вешающий на каждую `create policy … for select to anon using (true)`.

**Почему это проблема.** Под `anon` попадают `leads.raw_text` (текст обращения клиента),
`replies.body` (черновик ответа клиенту), `disagreements.reason` (внутренние оценки
менеджера). Комментарий рядом («публикуемому ключу — чтение») описывает намерение, но
политика шире намерения: сервер ходит секретным ключом, который RLS всё равно обходит,
поэтому anon-чтение здесь ничего не обслуживает — оно только расширяет поверхность.
Publishable-ключа в репозитории нет (проверено, см. вердикт), но такой ключ по своей
природе предназначен для браузера: как только к Supabase обратятся с фронта, чтение всей
базы станет публичным. Адрес проекта уже опубликован — находка 4.

**Что делать.** Снять `anon`-политику с `leads`, `scores`, `replies`, `disagreements`;
оставить при необходимости только `companies` (публичный реестр). Это правка `schema.sql`
плюс миграция; после неё перепроверить security advisors проекта.

### 7. СРЕДНЯЯ-НИЗКАЯ. Негативный контроль запрета сети печатает «работает» при любой ошибке

**Где.** `Makefile:21-24`.

**Почему это проблема.** Конструкция `python -c … 2>/dev/null && (провал) || echo "запрет сети работает"`
считает успехом любой ненулевой код возврата: сломанный импорт, опечатка в команде,
отсутствующий Python — всё напечатает «запрет сети работает». Это Р1 в обход правила:
«не смогли проверить» сворачивается в «годно», причём именно у того прибора, который
доказывает, что тесты не ходят в сеть (`ci.yml:13` запускает его перед самой сюитой).

**Воспроизведено (И2), ИЗМЕРЕНО:**

```
$ PYTHONPATH=ci python -c "import definitely_not_a_module; import urllib.request as u; u.urlopen('https://api.gleif.org/', timeout=5)" 2>/dev/null \
    && echo "ПРОВАЛ" || echo "запрет сети работает"
запрет сети работает        <- напечатано, хотя причина ImportError, а не запрет
```

**Сам запрет при этом настоящий** — проверено прямым прогоном с обоими контролями (И5):

```
$ PYTHONPATH=ci python -c "...urlopen('https://api.gleif.org/')"
BLOCKED BY: NetworkInTests тест пошёл в сеть — это запрещено: используйте OFFLINE=1 и кэш в data/
$ python -c "...urlopen('https://api.gleif.org/')"      # тот же вызов без запрета
сеть доступна без запрета: OK
```

**Что делать.** Проверять не код возврата, а исход: требовать в выводе `NetworkInTests`,
иначе печатать третий исход «не смогли проверить», а не «работает».

Рядом: `ci/no_network.py` и `ci/sitecustomize.py` — побайтово одинаковые файлы, а на
`PYTHONPATH` работает только второй (Python сам импортирует `sitecustomize`).
`no_network.py` не подключён нигде (`git grep no_network` вне этого отчёта — 0 совпадений).
Мёртвая копия рядом с рабочей даёт ложную уверенность и разъедется при первой правке (Е1).
